## Зачем
Исправление трёх дефектов из UI-приёмки v1.11.0 (отчёт `sprout_tests_UI/docs/claude/sprout-acceptance-report-2026-11-26.md`), все существовали до v1.11.0:
- **D4** — при оформлении заказа лимит проверялся по сумме цен за единицу без количества (для аккаунтов вне `LIMIT_APPROVAL_ACCOUNT_IDS`). Обычным пользователем воспроизводится: остаток снижен, пока корзина открыта → на стейдже создан заказ 740 ₽ при остатке 500 ₽.
- **D2** — при «Округлении итоговой суммы» (`account.priceRounding`) цена округлялась вверх, а старая цена — нет: 449,18 вместо 450 ₽, «Ваша выгода» занижена, у товаров без скидки — отрицательная.
- **D1** — покупатель с ролью «Менеджер», не руководящий ни одним подразделением, получал 404 «Поставка не найдена» при открытии позиции **своей** заявки в любом статусе.

## Изменения
- `basket.service.ts` (`createRequest`): сумма для проверки лимита — `Σ roundNumber(price × count)` для всех аккаунтов (раньше `price × count` только для аккаунтов из `LIMIT_APPROVAL_ACCOUNT_IDS`).
- `good.service.ts` (`list` и `listWithAvailability`): при `priceRounding` старая цена (`originalPrice`) округляется вверх так же, как `price`; `originalPriceWithTaxes` пересчитывается.
- `supply.service.ts`: новый `getByIdForViewOrFail` — только для `GET /api/supply/:id`; менеджер покупателя видит поставки подразделений, которыми руководит, **и свои**. `list()` получил опцию `includeOwnSupplies` (по умолчанию выключена), `ISupplyListFilters.ownUserId` → в репозитории `(subdivision_id IN (…) OR user_id = :ownUserId)`.
- **Не изменено намеренно:** `getByIdOrFail` (редактирование) и `checkExistence` (смена статуса) — прежние права. Сейчас по старому маршруту только это не даёт автору-менеджеру согласовать свою заявку (`validateStatus` разрешает `→ pending` любому с ролью Manager).

## Проверки
- Новые тесты (11), каждый исправленный сценарий падает без исправления:
  - `basket.service.spec.ts` — D4: 5 × 148 ₽ при остатке 500 ₽ → «Сумма в заявке превышает доступный лимит»; 3 × 148 = 444 ₽ — проверка лимита пройдена (2 теста).
  - `good.service.spec.ts` — D2: со скидкой Fit 10 % при 449,18 → `price` 405, `originalPrice` 450; без скидки `originalPrice` = `price` = 450; без `priceRounding` — без округления (3 теста).
  - `supply.view-access.spec.ts` — D1: менеджер без подразделений видит свою поставку; руководитель — подразделения + свои; `checkExistence` для менеджера не расширен (не находит свою поставку без подразделений, руководителю — только подразделения); покупатель без роли менеджера — как раньше; 404 при отсутствии (6 тестов).
- `yarn jest` полностью: 417 passed, 3 failed — те же 3 падают на чистом `dev` (`request.history.repository.spec.ts`, `feed.service.spec.ts` — snapshot/SQL, не связаны).
- `yarn build` — успешно.
- ESLint изменённых файлов: новых замечаний нет; 3 ошибки `import/order` в `basket.service.ts` и `good.service.ts` есть на чистом `dev`, не трогал.
- Стейдж (до исправления), API: менеджер-автор без подразделений `GET /api/supply/34721` (свой заказ в работе) → 404; автор без роли менеджера → 200.

## Совместимость и выпуск
- Миграций нет.
- API: контракт не меняется. `GET /api/supply/:id` для менеджеров покупателя теперь возвращает и их собственные поставки (раньше 404). `originalPrice`/`originalPriceWithTaxes` у аккаунтов с `priceRounding` — округлённые значения.
- D4 строже: заказы сверх остатка лимита с учётом количества теперь отклоняются сервером (фронт уже проверял так же — для пользователя в обычном сценарии ничего не меняется).
- Выкладка только back-end; связан с MR front-end по D3 (независимы).
