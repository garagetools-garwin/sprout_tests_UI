## Зачем
Дефект D3 из UI-приёмки v1.11.0: администратор покупателя не может установить персональный лимит 0 ₽. По модели лимитов «лимита нет» (`null`) и «0» — разные состояния: без лимита заявка уходит согласующему (для аккаунтов из `LIMIT_APPROVAL_ACCOUNT_IDS`) или ограничений нет, а 0 — «лимит кончился, закупки закрыты». Решено (26.11) дать ставить 0 в интерфейсе. Во фронте 0 трактовался как «пусто» в нескольких местах. Задача: без номера, дефект D3 из отчёта приёмки v1.11.0.

## Изменения
- Окно «2. Изменение персонального лимита»: можно ввести и сохранить 0 (минимум 0 вместо 1); при открытии остаток 0 показывается как `0.00`, а не очищается; «Сохранить» недоступна только при пустом поле; в обработчик передаётся число.
- `calculateUserBalance`: лимит 0 — заданный лимит (остаток считается), `null`/`undefined` — лимита нет.
- Список персональных лимитов: при остатке 0 показывается «0.00 ₽ остаток за период» (раньше ячейка пустая).
- Профиль и карточка пользователя: при лимите 0 блок «Персональный лимит» выводится; убран вывод лишнего «0» из-за `limit && …`.
- API и расчёты не меняются: на сервер уходит `limit = spentLimit + остаток` (при остатке 0 — `limit = spentLimit`), как и раньше для положительных значений.

- Новый `tests/personal-limit-zero.test.mjs` (5 тестов): остаток при `null`/`undefined`/0/исчерпанном/обычном лимите; окно — минимум 0, кнопка не зависит от `!balance`, начальное значение 0 не очищается. На старом коде падают 2 из 5.
- Все node-тесты: 78/78 (73 + 5).
- ESLint изменённых файлов: 0 ошибок, 0 новых предупреждений.
- Сборка в CI (pipeline MR, задача `build`): `yarn build` успешно. Проверка типов входит в сборку (`vite-plugin-checker`, `typescript: true`). Локально сборку не запускал: нет доступа к Nexus для `@axmit/garwin-api`.

## Совместимость и выпуск
- Миграций нет. API не меняется. Back-end уже принимает `limit = 0` (`@IsValidMoneyFormat`, без минимума).
- Выкладка только front-end; независим от MR back-end по D1/D2/D4.

## Ограничения проверки
- Не проверено на стенде, скриншотов и проверки на ширинах 375, 768 и 1440 px нет: меняется только условие показа, вёрстка та же. После выкладки на стейдж: автотест `sprout_tests_UI` `test_personal_limit_zero_can_be_saved` (D3) должен стать XPASS; руками — создать лимит 0, отредактировать существующий до 0, посмотреть список, профиль сотрудника и карточку пользователя.
- Сотрудник с лимитом 0 не может оформить заказ («Сумма в заявке превышает доступный лимит») — так и задумано; проверить на стейдже под ролью сотрудника.
