### D4. Заказ сверх личного лимита проходит через API

Фронт в обычном сценарии блокирует кнопку («Лимит превышен на 240.00 ₽»), но бэкенд принимает тот же заказ из устаревшей вкладки, старого клиента или прямого запроса.

1. Администратор покупателя выдаёт пользователю (аккаунт не в `LIMIT_APPROVAL_ACCOUNT_IDS`) персональный лимит 500 ₽.
2. Вкладка A: в корзине DDE 644-955 (148 ₽ без НДС) × 2, кнопка «Отправить» активна.
3. Вкладка B того же пользователя: количество 5 (сохраняется в корзину).
4. `POST /api/basket/request` с `goods[].count = 5`.

Факт: 201, заказ **#20261126-6823** на 740 ₽ при остатке 500 ₽, сразу `processing` (отменён после проверки). Ожидание: `400 Сумма в заявке превышает доступный лимит`.

**Воспроизводится и обычным пользователем, без инструментов разработчика:** у сотрудника остаток 1 000 ₽, в корзине 5 × 148 ₽ = 740 ₽, кнопка активна; пока корзина открыта, администратор снижает остаток до 500 ₽ (или лимит тратится другим заказом); сотрудник, не обновляя страницу, нажимает «Отправить» → 201, заказ #20261126-6829 на 740 ₽ при остатке 500 ₽ (отменён). Автотест: `test_order_over_personal_limit_is_rejected_by_server` (xfail).

Место: `back-end/src/modules/basket/basket.service.ts:199` (5f5df4b3) — `usesLimitApproval ? roundNumber(item.price * item.count) : item.price`: для аккаунтов вне списка суммируется цена за единицу. Ожидаемо: `price × count` для всех.

### D1. «Поставка не найдена» у заявки на согласовании

1. Автор открывает «Мои заказы» → «На согласовании» → любую заявку (воспроизведено на 6818, 6822, #4385).
2. Клик по названию позиции.

Факт: `GET /api/supply/{id} → 404`, toast «Поставка не найдена», карточка не открывается. Ожидание: карточка позиции или понятное сообщение, что на этом этапе она недоступна.

**Причина уточнена 27.11 — права, а не статус заявки:** `back-end/src/modules/supply/supply.service.ts` `list()` для покупателя с ролью «Менеджер» отдаёт только поставки подразделений, где он руководитель; если он нигде не руководитель — пусто, 404 даже по своей заявке в любом статусе (стейдж: автор-менеджер, свой заказ в работе → 404; автор без роли менеджера → 200). Исправлено в back-end MR !19. Автотест: `tests/test_price_display_and_limits.py::test_pending_request_item_opens_without_error` (xfail).

### D3. Нулевой персональный лимит

1. Настройки → Персональные лимиты → «Установить новый» → сотрудник → ввести 0.

Факт: «Сохранить» неактивна; в существующем лимите 0 превращается в 1. Ожидание: 0 — допустимое значение, отличное от «лимита нет». По модели доработки (Никита, 26.11): «нет лимита» — заявка уходит начальнику и списывается с его лимита; 0 — «лимит кончился, проси лимит». Решение (26.11, итог): сделать возможность поставить 0 в пользовательском интерфейсе — P2. Для такой загрузки: запрет закупок = `limit = 0`; `NULL` = «нет лимита» (в аккаунтах из `LIMIT_APPROVAL_ACCOUNT_IDS` — заявки к начальнику, в остальных — без ограничений).

Место: `front-end/src/entities/User/components/PersonalLimitChangeModal.tsx` — `:29` `balance ? … : null`, `:56` `disabled={!balance}`, `:72` `min={DEFAULT_VALUE_1}`. Автотест: `test_personal_limit_zero_can_be_saved` (xfail).

### D2 / D2a. Старая цена и выгода при округлении цен

У аккаунта включено «Округление итоговой суммы» (`priceRounding`). Договор №6, временная скидка на бренд Fit 10 %, F-33799 × 1 и × 2, три режима цен.

| Показатель | Ожидание | Факт (API корзины) |
| --- | --- | --- |
| Цена со скидкой, ₽ | 405,00 / 494,10 с НДС | 405 / 494,1 — верно |
| Старая цена (`originalPrice`), ₽ | 450,00 / 549,00 | 449,18 / 548 |
| «Ваша выгода» за 1 шт., режим «С НДС», ₽ | 54,90 | 53,90 |
| «Ваша выгода» за 1 шт., два других режима, ₽ | 45,00 | 44,18 |
| Итоги корзины, ₽ | 405 / НДС 89,10 / 494,10 | верно во всех режимах |

Причина: `price` округляется вверх (`Math.ceil`: 449,18 → 450; 404,26 → 405), а `originalPrice = item.price` — нет. Место: `back-end/src/modules/good/good.service.ts:327`, `:444`, `:503`, `:534`.

D2a — следствие: «Ваша выгода» в корзине = Σ (originalPrice − price) × count по всем строкам без ограничения снизу (`front-end/src/entities/Basket/Basket.helper.tsx:151`). Товары без скидки с дробной ценой дают отрицательную выгоду: в корзине из 5 строк вместо 88,36 показано 85,87 ₽. Исправление D2 закрывает и D2a.

## Вопросы к владельцу продукта

Первые два вопроса закрыты 26.11: обе переменные на проде при выпуске остаются пустыми — `CONTRACT_PRICE_DISPLAY_DEFAULTS` пустая даёт прежний вид цен (по коду), `LIMIT_APPROVAL_ACCOUNT_IDS=43` (ФосАгро) включается после настройки руководителей Кузьминой и проверки запросом готовности.

1. **`CONTRACT_PRICE_DISPLAY_DEFAULTS`** (на стейдже не задана). По README back-end без правила самостоятельно зарегистрированные покупатели видят цену с НДС, остальные — обе цены. Какие правила задать на проде до выпуска?
2. **`LIMIT_APPROVAL_ACCOUNT_IDS`** (на стейдже не задана, для теста включали аккаунт 7 и откатили). Каким аккаунтам включать новый маршрут? Данные стейджа (копия прода на 05.11): у ФосАгро (аккаунт 43) руководитель назначен в 7 из 125 подразделений, 24 сотрудника без личного лимита не смогут оформить заказ (2 из них заказывали за последние 90 дней). У них в каждом подразделении должен быть менеджер с ролью manager, а у согласующих — личные лимиты, иначе заказы не оформляются или не согласуются.
3. **Округление (Q1).** «Округление итоговой суммы» на деле округляет вверх **цену за единицу**: 449,18 → 450 ₽ за штуку, при 1 000 шт. покупатель платит на 820 ₽ больше, чем при округлении итога. Так задумано? (Существовало до MR.)
4. **Контакт в 1С (Q2).** В новом маршруте заказ уходит в 1С от имени согласующего (`order.user` = плательщик): ФИО, телефон и email — его, автор только в комментарии «Согласование заказа - …». Это устраивает тех, кто работает с заказами в 1С?
5. **N1 / N10.** Может ли продавец видеть и менять заявку до финального согласования у покупателя?
6. **Общий лимит подразделения** резервируется при отправке заявки, до согласования, и возвращается при отклонении или отмене. Если правило другое — уточнить.
